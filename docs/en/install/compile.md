## Operator Package Form Introduction

- **Custom operator package**:

  The package generated by compiling selected operators is called a custom operator package. It applies to the CANN package in **mount** form and does not change the original package content. The generated custom operator package has a higher priority than the original CANN package. This package supports calling AI Core and AI CPU operators through aclnn and graph mode.

- **ops-transformer package**:

  The package generated by compiling the entire project is called the ops-transformer package. It can **completely replace** the corresponding part of the CANN package. This package supports calling AI Core operators through aclnn and graph mode.

- **ops-transformer static library**:

  > Note: If you need to **perform secondary release based on this project** and have **requirements on the software package size**, it is recommended to use static library compilation. This library can be linked to your application development program and only retains the operators required by the business, thereby implementing minimal software deployment.

  It indicates that the entire project is compiled into a static library file, including libcann_transformer_static.a and aclnn API header files. This package only supports calling AI Core operators through aclnn.

## Online Compilation

If compilation is performed in an environment with internet access, third-party dependencies will automatically be installed during compilation, and no manual installation is required. The source code compilation and deployment commands in different scenarios are as follows:

### Custom Operator Package

1. **Compile the custom operator package**

    Enter the project root directory and execute the following compile command:

    ```bash
    bash build.sh --pkg --soc=${soc_version} [--vendor_name=${vendor_name}] [--ops=${op_list}] [--opkernel_aicpu] [--kernel_template_input=${kernel_template_input}]
    # Take FlashAttentionScore operator compilation as an example
    # bash build.sh --pkg --soc=ascend910b --ops=flash_attention_score
    # A6 PR: compile operators registered with the ascend960pr configuration
    # bash build.sh --pkg --soc=ascend960pr --ops=flash_attention_score_grad
    # Compile operators in the experimental contribution directory
    # bash build.sh --pkg --experimental --soc=ascend910b --ops=${experimental_op}
    # Specify the tilingKey template to compile only the kernel variants matching the template parameters (take add_example as an example, compile only the float variant)
    # bash build.sh --pkg --soc=ascend910b --ops=add_example --kernel_template_input="schMode=0"
    ```

    - --soc: \$\{soc\_version\} indicates the NPU model. Atlas A2 products use "ascend910b" (default), Atlas A3 products use "ascend910_93", Ascend 950PR&950DT products use "ascend950", A6 DT uses "ascend960dt", and A6 PR uses "ascend960pr" (corresponding to Ascend960PR_969A1). A6 compilation requires installing a CANN toolchain that supports the corresponding model. The supported operator range is subject to its SoC registration configuration.
    - --vendor_name (optional): \$\{vendor\_name\} indicates the name of the custom operator package to build. The default name is custom.
    - --ops (optional): \$\{op\_list\} indicates the operators to compile. If not specified, all operators are compiled by default. The format is like "apply_rotary_pos_emb,rope_quant_kvcache,...", and multiple operators are separated by English commas ",".
    - --experimental (optional): indicates compiling operators in the experimental contribution directory. ${experimental_op} is the name of the new contribution operator directory.
    - --opkernel_aicpu (optional): enables ENABLE_AICPU_KERNEL to compile kernel_aicpu.
    - --kernel_template_input (optional): \$\{kernel\_template\_input\} indicates the tilingKey template specified when compiling the kernel. Only kernel variants matching the template parameters are compiled. The format is like "Parameter=value", and multiple parameter groups are separated by English commas ",". Boolean parameters take the value false/true. The template parameter names and value ranges come from the declaration of `ASCENDC_TPL_ARGS_DECL` in the `*_tiling_key.h` file under the operator op_kernel directory, where the first argument of each `ASCENDC_TPL_*_DECL` macro is the parameter name, and `ASCENDC_TPL_SEL` lists the instantiated values of each parameter. This option must be used together with --ops, and at this point --ops only supports specifying a single operator (multiple operators separated by English commas "," are not supported). Otherwise, the compilation reports the error "--kernel_template_input must be used with --ops= and can only specify a single operator". At the same time, the binary files of other operators that this operator depends on will not be compiled.

    > **Note**: When compiling pure AI CPU operators (operators that contain only the op_kernel_aicpu directory), the --opkernel_aicpu option must be added. Otherwise, the error "OpFileNotExistsError: File aic-*-ops-info.ini does not exist" is reported. For details, see the FAQ section below.
    >
    > By default, full compilation generates all tiling key kernel variants registered by the operator. When there are many variants, compilation takes a long time. When only a specific template combination needs to be debugged or verified, use --kernel_template_input to compile only the matching variants, which speeds up compilation and reduces the package size. Take add_example as an example. This operator declares the template parameter schMode in [add_example_tiling_key.h](../../../examples/add_example/op_kernel/add_example_tiling_key.h) (0 indicates float, 1 indicates int32). Full compilation generates 2 variants. The command to compile only the float variant is as follows:
    >
    > ```bash
    > bash build.sh --pkg --soc=ascend910b --ops=add_example --kernel_template_input="schMode=0"
    > ```
    >
    > When an operator declares multiple template parameters, multiple "Parameter=value" groups can be specified simultaneously, with the format like --kernel_template_input="X_LAYOUT=1,X_DTYPE=2,HAS_MASK=true". When only some template parameters are specified, the unspecified parameters are expanded in all combinations according to the registered values. Note: The trimmed operator package contains only the specified variants. When running scenarios with other template combinations, an error is reported because the corresponding kernel binary is missing. It is only applicable to debugging or verification in the corresponding scenario.

    If neither \$\{vendor\_name\} nor \$\{op\_list\} is passed in, the ops-transformer package is compiled. To compile a custom operator package of all operators, pass in \$\{vendor\_name\}. When the following information is displayed, it indicates successful compilation.

    ```bash
    Self-extractable archive "cann-ops-transformer-${vendor_name}_linux-${arch}.run" successfully created.
    ```

    After successful compilation, the run package is stored in the build_out directory under the project root directory.

2. **Install the custom operator package**

    ```bash
    ./cann-ops-transformer-${vendor_name}_linux-${arch}.run
    ```

    The installation path of the custom operator package is ```${ASCEND_HOME_PATH}/opp/vendors```. \$\{ASCEND\_HOME\_PATH\} is configured through an environment variable and indicates the installation path of the CANN toolkit package, generally \$\{install\_path\}/cann.

    > After installation, run `grep load_priority ${ASCEND_HOME_PATH}/opp/vendors/config.ini` to verify. The expected output contains this vendor. If there is no output, the owner or permission of `${ASCEND_HOME_PATH}/opp/vendors` is usually incorrect. Troubleshoot and then reinstall.

    If the installation directory of the operator package is specified through the --install-path parameter during deployment, before using the custom operator, execute the ```source ${install_path}/vendors/${vendor_name}/bin/set_env.bash``` command. The set_env.bash script appends the installation path of the custom operator package to the environment variable ASCEND_CUSTOM_OPP_PATH, so that the custom operator takes effect in the current environment.

3. **(Optional) Delete the custom operator package**

    Note that the custom operator package does not support uninstallation. To uninstall it, delete the vendors\/\$\{vendor\_name} directory and delete the configuration item corresponding to \$\{vendor\_name\} in load_priority in vendors/config.ini.

### ops-transformer Package

1. **Compile the ops-transformer package**

    Enter the project root directory and execute the following compile command:

    ```bash
    # Compile all operators except those in the experimental contribution directory
    bash build.sh --pkg --soc=${soc_version}
    # A6 PR
    # bash build.sh --pkg --soc=ascend960pr
    # Build A6 DT and PR simultaneously
    # bash build.sh --pkg --soc=ascend960dt,ascend960pr
    # Specify the packaging type (run/rpm/deb/all), default run
    # bash build.sh --pkg --pkg-type=deb --soc=${soc_version}
    # Compile all operators in the experimental contribution directory
    # bash build.sh --pkg --experimental --soc=${soc_version}
    ```

    - --soc: \$\{soc\_version\} indicates the NPU model. Atlas A2 products use "ascend910b" (default), Atlas A3 products use "ascend910_93", and Ascend 950PR&950DT products use "ascend950".
    - --pkg-type (optional): specifies the packaging type. The value is run/rpm/deb/all, and the default is run. It can only be used together with --pkg.
    - --experimental (optional): indicates compiling operators in the experimental contribution directory.

    If the following information is displayed, it indicates successful compilation.

    ```bash
    Self-extractable archive "cann-${soc_name}-ops-transformer_${cann_version}_linux-${arch}.run" successfully created.
    ```

    \$\{soc\_name\} indicates the NPU model name, that is, the remaining content after removing "ascend" from \$\{soc\_version\}. After successful compilation, the run package is stored in the build_out directory.

2. **Install the ops-transformer package**

    ```bash
    # Install command
    ./cann-${soc_name}-ops-transformer_${cann_version}_linux-${arch}.run --full --install-path=${install_path}
    ```

    \$\{install\_path\}: indicates the specified installation path. It needs to be installed in the same path as the toolkit package. By default, it is installed in the `/usr/local/Ascend` directory.

3. **(Optional) Uninstall the ops-transformer package**

    ```bash
    # Uninstall command
    ./${install_path}/cann/share/info/ops_transformer/script/uninstall.sh
    ```

### ops-transformer Static Library

> Note: The static library only supports Atlas A2, Atlas A3, and Atlas A5 products. The static library is not supported for experimental operators.

1. **Compile the ops-transformer static library**

    Enter the project root directory and execute the following compile command:

    ```bash
    bash build.sh --pkg --static --soc=${soc_version}
    ```

    \$\{soc\_version\} indicates the NPU model. Atlas A2 products use "ascend910b" (default), Atlas A3 products use "ascend910_93", and Atlas A5 products use "ascend950".
    If the following information is displayed, it indicates successful compilation and compression.

    ```bash
    [SUCCESS] Build static lib success!
    Successfully created compressed package: ${repo_path}/build_out/cann-${soc_name}-ops-transformer-static_${cann_version}_linux-${arch}.tar.gz
    ```

    \$\{repo\_path\} indicates the project root directory, and \$\{soc\_name\} indicates the NPU model name, that is, the remaining content after removing "ascend" from \$\{soc\_version\}. After successful compilation, the compressed package is stored in the build_out directory.

2. **Decompress the ops-transformer static library**

    Enter the build_out directory and execute the decompression command:

    ```bash
    tar -zxvf ./cann-${soc_name}-ops-transformer-static_${cann_version}_linux-${arch}.tar.gz -C ${static_lib_path}
    ```

    \$\{static\_lib\_path\} indicates the decompression path of the static library. The directory structure after decompression is as follows:

    ```text
    ├── cann-${soc_name}-ops-transformer-static_${cann_version}_linux-${arch}
    │   ├── lib64
    │   │   ├── libcann_transformer_static.a        # Static library file
    │   └── include
    |       ├── ...                                 # aclnn API header files
    ```

## Offline Compilation

If compilation is performed in an environment without internet access, prepare the dependent third-party software in advance, and then perform source code compilation. The specific process is as follows:

1. **Check whether the basic environment is complete**

    Please ensure that the basic environment has been set up according to [Environment Deployment](../install/quick_install.md), including CANN package installation and source code download.

    - In an online environment, enter the [project homepage](https://atomgit.com/cann/ops-transformer), and use the `Download ZIP` or `clone` button to complete the source code download according to the instructions.
    - Connect to the offline environment and upload the source code to the directory you specify. If the downloaded source code is a compressed package, decompress it first.

2. **Download third-party software dependencies**

    Download third-party software in advance in an online environment. The following methods are available. Select one as needed:

    - Method 1: Manually download according to the table provided in [Third-Party Software Dependencies](#installing-third-party-dependencies). If downloading from other addresses, please ensure the version numbers are consistent.

    - Method 2: Download with one click through the [download_3rd_party.sh](../../../scripts/download_3rd_party.sh) script. This script is in the `scripts/` directory of this project and can download all third-party components involved in this project with one click (including cann-cmake, source packages of each third-party component, required patches, and git repositories such as opbase/ops-tensor/catlass). By default, they are stored in the `third_party` directory under the project root directory. Execute the following command:

        ```bash
        bash scripts/download_3rd_party.sh
        # You can also specify the storage directory of third-party components, and pass it through --cann_3rd_lib_path=<directory> during compilation
        # bash scripts/download_3rd_party.sh --cann_3rd_lib_path=${cann_3rd_lib_path}
        ```

    > **Note**:
    >
    > - The script performs SHA256 integrity verification on each file. On a second call, files that have been downloaded and passed verification are automatically skipped, and no repeated download is required.
    > - Some third-party components in this repository (such as abseil-cpp and makeself) require patches to be applied during compilation and build. Patches are uniformly stored in the `patch` subdirectory under the third-party component directory (that is, `${cann_3rd_lib_path}/patch`). The script automatically downloads the required patches, and no manual processing is required.
    > - opbase/ops-tensor/catlass are git repositories. The script automatically clones them to `${cann_3rd_lib_path}` (git must be installed on the local machine). If the directory already exists, the script verifies whether its current HEAD is the target commit. If not, it automatically fetches and checks out to the target commit.
    > - If the above directory already exists but is not a git repository (for example, a manually decompressed source code directory), the script reports an error and exits without deleting the directory content. Manually delete the directory, change the storage directory, or prepare a repository of the correct version yourself.

3. **Compile the operator package**

   Upload the downloaded third-party software to the offline environment. It can be stored in the `third_party` directory or a custom directory. **The former is recommended, and its compile command is consistent with the command in the online compilation scenario.**

    - **third\_party directory **(recommended)**

      Create a `third_party` directory under the project root directory (no need to create it if it already exists), and copy the third-party software to the specified directory. At this point, the compile command is consistent with the online compilation command. For details, refer to [Online Compilation](#online-compilation).

    - **Custom directory**

      Create a `${cann_3rd_lib_path}` directory at any location in the offline environment, and copy the third-party software to this directory. Please ensure that this directory has access permission.

        ```bash
      mkdir -p ${cann_3rd_lib_path}
        ```

      At this point, the compile command needs to additionally add `--cann_3rd_lib_path=${cann_3rd_lib_path}` on the basis of the online compilation command to specify the path where the third-party software is located. Assuming the storage path is `/path/cann_3rd_lib_path`, the commands corresponding to different compilation methods are as follows:

      - Custom operator package

        ```bash
        bash build.sh --pkg --soc=${soc_version} [--vendor_name=${vendor_name}] [--ops=${op_list}] --cann_3rd_lib_path=${cann_3rd_lib_path}
        # Take FlashAttentionScore operator compilation as an example
        # bash build.sh --pkg --soc=ascend910b --ops=flash_attention_score --cann_3rd_lib_path=/path/cann_3rd_lib_path
        ```

      - ops-transformer full package

        ```bash
        bash build.sh --pkg --soc=${soc_version} --cann_3rd_lib_path=${cann_3rd_lib_path}
        # bash build.sh --pkg --soc=ascend910b --cann_3rd_lib_path=/path/cann_3rd_lib_path
        ```

      - ops-transformer static library

        ```bash
        bash build.sh --pkg --static --soc=${soc_version} --cann_3rd_lib_path=${cann_3rd_lib_path}
        # bash build.sh --pkg --static --soc=ascend910b --cann_3rd_lib_path=/path/cann_3rd_lib_path
        ```

4. **Install/uninstall the operator package**

    The operator packages obtained from offline and online compilation are the same. By default, they are stored in the build_out directory under the project root directory, and the install and uninstall commands are also the same. For details, see [Online Compilation](#online-compilation).

## Local Verification

After the source package is deployed, execute UT test cases through build.sh in the project root directory to verify whether the project functions work properly.

> Note: Executing UT test cases depends on the googletest unit test framework. For details, visit the [GoogleTest website](https://google.github.io/googletest/advanced.html#running-a-subset-of-the-tests).

```bash
# Install the test-related requirements.txt dependencies under the root directory
pip3 install -r tests/requirements.txt
# Method 1: compile and execute the UT test cases of the specified operator and corresponding function (choose one)
bash build.sh -u --[opapi|ophost|opkernel] --ops=add_example
# Method 2: compile and execute all UT test cases
# bash build.sh -u
# Method 3: compile all UT test cases but do not execute
# bash build.sh -u --noexec
# Method 4: compile and execute the UT test cases of the corresponding function (choose one)
# bash build.sh -u --[opapi|ophost|opkernel]
# Method 5: compile the UT test cases of the corresponding function but do not execute (choose one)
# bash build.sh -u --noexec --[opapi|ophost|opkernel]
# Method 6: specify soc compilation when executing UT test cases
# bash build.sh -u --[opapi|ophost|opkernel] [--soc=${soc_version}]
```

Take verifying whether the ophost function works properly as an example. Execute the following command:

```bash
bash build.sh -u --ophost
```

After execution, the following content appears, indicating successful execution.

```bash
Global Environment TearDown
[==========] ${n} tests from ${m} test suites ran. (${x} ms total)
[  PASSED  ] ${n} tests.
[100%] Built target math_op_host_ut
```

\$\{n\} indicates that n test cases were executed, \$\{m\} indicates m tests, and \$\{x\} indicates the time consumed to execute the test cases, in milliseconds.
> Note: The add_example operator is only intended to help understand how to develop operators. Only the ophost UT test case is designed, and no opapi or opkernel UT test cases are designed. Developers can refer to the UT test cases of other operators for implementation and maintenance.

## FAQ

### Local compilation reports the error "ERROR: No matching distribution found for setuptools>=40.8.0"

```bash
Could not fetch URL XXX (Caused by SSLError(SSLCertVerificationError))
ERROR: Could not find a version that satisfies the requirement setuptools>=40.8.0 (from versions: none)
ERROR: No matching distribution found for setuptools>=40.8.0
```

1. Check whether the Python third-party library dependencies in requirements.txt under the root directory in [Environment Deployment](./quick_install.md) are complete.

2. Check whether the pip source specified in ~/.pip/pip.conf or ~/.config/pip/pip.conf in the environment is available.

### Error when compiling aicpu operators separately

When compiling pure AI CPU operators separately (operators that contain only the op_kernel_aicpu directory), if the --opkernel_aicpu option is not added, the following error occurs:

```bash
OpFileNotExistsError: File aic-*-ops-info.ini does not exist in directory [...]
make: *** [Makefile:462: prepare_build] Error 2
```

The cause of this error is that ENABLE_AICPU_KERNEL is not enabled, resulting in the aic-*-ops-info.ini file not being generated. Add the --opkernel_aicpu option to the compile command, for example:

```bash
bash build.sh --pkg --soc=${soc_version} --ops=${op_list} --opkernel_aicpu
```

### Recovery after compilation failure or interruption

Compilation failure or forced interruption may cause build cache corruption. When compilation is abnormal again, run `bash build.sh --make_clean` to clean up and then recompile.
